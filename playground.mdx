| Query | What it answers |
|---|---|
| [`residentialPlans`](/queries/residential-plans) | Residential plans, rates, fees and enrollment links for a ZIP |

The Docs panel on the left of the playground is generated from the live schema, so autocomplete and
field documentation always match what the API actually returns today.

## What it will not run

`utilityAccounts` is **not available** in the public playground. It looks up real customer service
accounts by street address, so it stays behind an issued API key. The playground is read-only:
mutations and subscriptions are rejected.

## Using it from code, or from an AI agent

The playground endpoint is a plain GraphQL endpoint. It needs no key, no authentication header and
no browser, so a script or an AI coding assistant can call it directly:

```bash
curl -s -X POST https://powerhq-playground-api.powerhq.workers.dev/graphql \
  -H "Content-Type: application/json" \
  -d '{"query": "{ utilities(zipCode: \"75231\") { id name } }"}'
```

**Schema introspection is enabled and does not count against the limit**, so an agent can discover
the whole API in one call before writing a query:

```bash
curl -s -X POST https://powerhq-playground-api.powerhq.workers.dev/graphql \
  -H "Content-Type: application/json" \
  -d '{"query": "{ __schema { queryType { fields { name } } } }"}'
```

Responses carry `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` so a client can
see its own budget. Over the limit the endpoint returns `429` with a GraphQL-shaped error.

## Moving to your own key

With an issued key you skip the playground and call production directly, with no per-day cap:

```bash
curl -s -X POST https://eapi.prod.powerhq.co/graphql \
  -H "x-api-key: YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query": "{ utilities(zipCode: \"75231\") { id name } }"}'
```
