---
title: "Enrollment URLs: Pass Customer Context Into Checkout"
sidebarTitle: "enrollmentUrl"
description: "Generate an enrollment link that carries what you already know about the customer: name, email, phone, usage and price type, so they do not re-enter it at checkout."
---

Every plan already comes with `enrollmentUrl` and `headlessEnrollmentUrl` stamped with your partner
code. Those links start the customer at the beginning of checkout.

`residentialEnrollmentUrl` and `businessEnrollmentUrl` do more: you hand us what you already know
about the customer, and we return a link that carries it into the flow. The customer does not retype
their name, and the price they saw on your site is the price checkout quotes.

## residentialEnrollmentUrl

```graphql
{
  residentialEnrollmentUrl(
    planId: "e895bd03-eec0-4f5b-862a-b799109d93fa"
    zipCode: "77002"
    monthlyUsage: 1500
    priceType: "FLAT"
    customer: {
      firstName: "Jordan"
      lastName: "Lee"
      email: "jordan@example.com"
      phone: "7135550142"
    }
  ) {
    enrollmentUrl
    headlessEnrollmentUrl
  }
}
```

Returns:

```
https://www.powerhq.co/app.html?utm_source=YOUR_CODE&utm_medium=referral&utm_campaign=partners#/redirect
  ?ftype=RESIDENTIAL_PARTNER
  &plan_id=e895bd03-eec0-4f5b-862a-b799109d93fa
  &zip_code=77002
  &ref=YOUR_CODE
  &fname=Jordan&lname=Lee&email=jordan%40example.com&phone=7135550142
  &annual_usage=18000.0&usage_source=EXTERNAL&is_flat=true
```

### Arguments

<ParamField query="planId" type="String" required>
  The `id` from a `residentialPlans` result. Plan ids regenerate when the catalog refreshes, so
  generate the link at the moment the customer picks a plan rather than storing it.
</ParamField>

<ParamField query="zipCode" type="String" required>
  Five-digit ZIP of the service location.
</ParamField>

<ParamField query="customer" type="EnrollmentCustomerInput">
  `firstName`, `lastName`, `email`, `phone`. Each supplied field lands in the link as `fname`,
  `lname`, `email` and `phone`, and prefills the enrollment form. Send only what you actually hold.
</ParamField>

<ParamField query="monthlyUsage" type="Long">
  The customer's monthly kWh, if you already know it. Carried into the link as
  `annual_usage` (`monthlyUsage` × 12) with `usage_source=EXTERNAL`, so checkout prices at their real
  usage instead of the 1000 kWh default.

  Omit it and the link carries no usage parameters at all, and checkout falls back to its own estimate.
</ParamField>

<ParamField query="priceType" type="String">
  `"SEASONALIZED"` (the default) or `"FLAT"`. `"FLAT"` adds `is_flat=true` to the link, so checkout
  prices the plan the same way your UI did. See [Pricing](/concepts/pricing).
</ParamField>

<ParamField query="startDate" type="Date">
  Requested service start date.
</ParamField>

<ParamField query="utilityAccountNumber" type="String">
  The customer's ESID or utility account number, if you have resolved one via
  [`utilityAccounts`](/queries/utility-accounts).
</ParamField>

<ParamField query="address" type="EnrollmentAddressInput">
  `street`, `street2`, `city`, `state`.

  <Warning>
    Accepted, but it does **not** change the returned link. Passing an address produces a URL
    identical to one generated without it, so do not rely on it to prefill the service address today.
  </Warning>
</ParamField>

## businessEnrollmentUrl

Same idea, with the fields a commercial enrollment needs.

```graphql
{
  businessEnrollmentUrl(
    planId: "9b740dd9-9a5d-48fe-976a-0cb5ed4cdebb"
    zipCode: "77002"
    isMoveIn: false
    annualUsageInkWh: 50000
    businessName: "Acme Coffee"
    position: "Owner"
    customer: {
      firstName: "Jordan"
      lastName: "Lee"
      email: "jordan@example.com"
      phone: "7135550142"
    }
  ) {
    enrollmentUrl
  }
}
```

Returns a link carrying `bname=Acme+Coffee`, `position=Owner`, `is_move_in=false` and
`annual_usage=50000.0` alongside the customer fields.

`isMoveIn` is **required** here and has no residential equivalent: a business enrollment has to declare
whether it is a switch or a new location.

## Which URL to use

| Field | Use it when |
|---|---|
| `enrollmentUrl` | You want the full PowerHQ checkout page, with its own header and footer |
| `headlessEnrollmentUrl` | You are embedding checkout in your own page or a webview and want it bare |

Both carry identical parameters. They differ only in chrome.

## What the parameters mean

| Parameter | Where it comes from |
|---|---|
| `fname`, `lname`, `email`, `phone` | Your `customer` input |
| `annual_usage` | `monthlyUsage` × 12, residential. `annualUsageInkWh` verbatim, business |
| `usage_source=EXTERNAL` | Present whenever you supplied usage, telling checkout the number came from you |
| `is_flat=true` | Present when `priceType: "FLAT"` |
| `bname`, `position`, `is_move_in` | Business only |
| `plan_id`, `zip_code`, `ref`, `ftype` | Always present |
| `utm_source`, `utm_medium`, `utm_campaign` | Set by PowerHQ from your partner code |

<Note>
  **Campaign attribution is not partner-settable on these links today.** `utm_campaign` is fixed to
  `partners`. If you need per-campaign reporting through the API, talk to your partner manager. The
  [Drop-in Storefront](/storefront) does support a free-form `utm_campaign`.
</Note>

<Warning>
  These links carry personal data in the query string. Generate them server-side at the moment the
  customer acts, hand the URL straight to the browser, and do not log or cache it.
</Warning>
