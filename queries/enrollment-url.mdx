title: "Enrollment URLs: Pass Customer Context Into Checkout"
sidebarTitle: "enrollmentUrl"
description: "Generate an enrollment link that carries what you already know about the customer: name, email, phone, usage and service account, so they do not re-enter it at checkout."
---

Every plan already comes with `enrollmentUrl` and `headlessEnrollmentUrl` stamped with your partner
code. Those links start the customer at the beginning of checkout.

`residentialEnrollmentUrl` and `businessEnrollmentUrl` do more: you hand us what you already know
about the customer, and we return a link that carries it into the flow. The customer does not retype
their name, and the price they saw on your site is the price checkout quotes.

## residentialEnrollmentUrl

```graphql
{
  residentialEnrollmentUrl(
    planId: "e895bd03-eec0-4f5b-862a-b799109d93fa"
    zipCode: "77002"
    monthlyUsage: 1500
    utilityAccountNumber: "1008901000158230011100"
    customer: {
      firstName: "Jordan"
      lastName: "Lee"
      email: "jordan@example.com"
      phone: "7135550142"
    }
  ) {
    enrollmentUrl
    headlessEnrollmentUrl
  }
}
```

Returns:

```
https://www.powerhq.co/app.html?utm_source=YOUR_CODE&utm_medium=referral&utm_campaign=YOUR_CAMPAIGN#/redirect
  ?ftype=RESIDENTIAL_PARTNER
  &plan_id=e895bd03-eec0-4f5b-862a-b799109d93fa
  &zip_code=77002&state=TX
  &ref=YOUR_CODE
  &prospect_id=v2-190CEF10D75DE22D91098CED077D4250
  &fname=Jordan&lname=Lee&email=jordan%40example.com&phone=7135550142
  &annual_usage=18000.0&usage_source=EXTERNAL
```

## Prefilling the service address

This is a two-step flow, and the address itself is not what you pass.

<Steps>
  <Step title="Find the account with utilityAccounts">
    Query [`utilityAccounts`](/queries/utility-accounts) by **ESID if you have one**, which is the
    reliable path:

    ```graphql
    { utilityAccounts(accountNumber: "1008901000158230011100") { accountNumber } }
    ```

    If you only have an address, you can look it up that way instead, but the match is strict: `street`
    has to be spelled the way the utility spelled it, units included, and `street2` is compared exactly.
    Prefer the ESID whenever the customer can give you one.
  </Step>
  <Step title="Pass the accountNumber as utilityAccountNumber">
    Take `accountNumber` from the result and send it on the enrollment-URL query.
  </Step>
  <Step title="We resolve it into the link">
    The returned URL gains **`prospect_id`** (our internal id for that service account) and **`state`**.
    That is what attaches the service address to the enrollment.
  </Step>
</Steps>

<Warning>
  **Pass the ESID, not the account `id`.** `utilityAccounts` returns both. Sending the `v2-…` id as
  `utilityAccountNumber` is accepted and silently does nothing: the link comes back without
  `prospect_id`. Only the numeric `accountNumber` resolves.

  The `address` argument behaves the same way. It is accepted, and it does not attach anything on its
  own. Use `utilityAccountNumber`.
</Warning>

### Arguments

<ParamField query="planId" type="String" required>
  The `id` from a `residentialPlans` result. Plan ids regenerate when the catalog refreshes, so
  generate the link at the moment the customer picks a plan rather than storing it.
</ParamField>

<ParamField query="zipCode" type="String" required>
  Five-digit ZIP of the service location.
</ParamField>

<ParamField query="utilityAccountNumber" type="String">
  The customer's ESID or utility account number, from
  [`utilityAccounts`](/queries/utility-accounts). This is what attaches the service address. See above.
</ParamField>

<ParamField query="customer" type="EnrollmentCustomerInput">
  `firstName`, `lastName`, `email`, `phone`. Each supplied field lands in the link as `fname`,
  `lname`, `email` and `phone`, and prefills the enrollment form. Send only what you actually hold.
</ParamField>

<ParamField query="monthlyUsage" type="Long">
  The customer's monthly kWh, if you already know it. Carried into the link as
  `annual_usage` (`monthlyUsage` × 12) with `usage_source=EXTERNAL`, so checkout prices at their real
  usage instead of the 1000 kWh default.

  Omit it and the link carries no usage parameters at all, and checkout falls back to its own estimate.
</ParamField>

<ParamField query="priceType" type="String">
  Leave this alone unless you have a specific reason not to. It defaults to `"SEASONALIZED"`, the
  all-in rate accounting for how usage changes across the year, which is the number your plan cards
  show.

  Passing `"FLAT"` adds `is_flat=true` and prices every month at the exact `monthlyUsage` you supplied,
  with no seasonal adjustment. See [Pricing](/concepts/pricing).
</ParamField>

<ParamField query="startDate" type="Date">
  Requested service start date.
</ParamField>

<ParamField query="address" type="EnrollmentAddressInput">
  `street`, `street2`, `city`, `state`. Accepted, but see the warning above: it does not attach the
  service address on its own. Use `utilityAccountNumber`.
</ParamField>

## businessEnrollmentUrl

Same idea, with the fields a commercial enrollment needs.

```graphql
{
  businessEnrollmentUrl(
    planId: "9b740dd9-9a5d-48fe-976a-0cb5ed4cdebb"
    zipCode: "77002"
    isMoveIn: false
    annualUsageInkWh: 50000
    businessName: "Acme Coffee"
    position: "Owner"
    customer: {
      firstName: "Jordan"
      lastName: "Lee"
      email: "jordan@example.com"
      phone: "7135550142"
    }
  ) {
    enrollmentUrl
  }
}
```

Returns a link carrying `bname=Acme+Coffee`, `position=Owner`, `is_move_in=false` and
`annual_usage=50000.0` alongside the customer fields.

`isMoveIn` is **required** here and has no residential equivalent: a business enrollment has to declare
whether it is a switch or a new location.

## Campaign tracking

The `utm_` parameters sit in the ordinary query string, before the `#`:

```
https://www.powerhq.co/app.html?utm_source=YOUR_CODE&utm_medium=referral&utm_campaign=YOUR_CAMPAIGN#/redirect?...
```

Set `utm_campaign` to whatever you want to report on, exactly as you would on a
[Drop-in Storefront](/storefront) link. Whatever it holds at the moment of conversion is what lands in
your daily conversion file and your monthly commission report. Some partners pass campaign name,
placement or ad set directly; others pass a unique id and match it back in their own systems.

<Warning>
  Keep your `utm_` parameters **before** the `#`. Anything placed after it is part of the app's own
  fragment and will not be captured for attribution.
</Warning>

## Which URL to use

| Field | Use it when |
|---|---|
| `enrollmentUrl` | You want the full PowerHQ checkout page, with its own header and footer |
| `headlessEnrollmentUrl` | You are embedding checkout in your own page or a webview and want it bare |

Both carry identical parameters. They differ only in chrome.

## What the parameters mean

| Parameter | Where it comes from |
|---|---|
| `fname`, `lname`, `email`, `phone` | Your `customer` input |
| `prospect_id`, `state` | Resolved from the `utilityAccountNumber` you supplied |
| `annual_usage` | `monthlyUsage` × 12, residential. `annualUsageInkWh` verbatim, business |
| `usage_source=EXTERNAL` | Present whenever you supplied usage, telling checkout the number came from you |
| `is_flat=true` | Present only when you override `priceType` to `"FLAT"` |
| `bname`, `position`, `is_move_in` | Business only |
| `plan_id`, `zip_code`, `ref`, `ftype` | Always present |
| `utm_source`, `utm_medium`, `utm_campaign` | Yours to set, before the `#` |

<Warning>
  These links carry personal data in the query string. Generate them server-side at the moment the
  customer acts, hand the URL straight to the browser, and do not log or cache it.
</Warning>
